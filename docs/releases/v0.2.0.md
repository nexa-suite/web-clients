# Nexa Web Clients 0.2.0 candidate

Status: frozen-scope source candidate prepared for stable release review. No `v0.2.0` tag, published artifact, or deployment has been created yet. The source tag is gated on the remaining integration check and source review below. Product/UX acceptance, connected-system acceptance and production readiness remain distinct later gates; none is claimed here.

## Candidate scope

- Keep Platform workforce operations and Buyer Portal as separate surfaces over the canonical 11 Bounded Contexts and shared typed API boundary.
- Add Platform access-context selection, membership/role administration, Warehouse access grants, Company Owner support consent, and a separate internal onboarding/support console.
- Add Buyer catalog search/detail, server-backed Purchase Request drafts and submission, request/order views, Buyer delivery list/detail, supplier-wallet balance/ledger/recharge and order-tender choice, credit/receivables display, and business-document access/download.
- Add Platform Purchase Request review/conversion/rejection, warehouse fulfillment and dispatch workbench, operational overview, credit configuration, wallet refunds, document access, and explicit order-summary generation requests.
- Use API-issued permissions and Tenant/Workspace scope as presentation and request inputs; durable authorization and commercial, inventory, credit, payment, fulfillment, delivery and document facts remain server-owned.
- Adopt Design Lab token JSON as the canonical source for generated SCSS layers, retain the shared UI library through its public API, and preserve production focus-visible/skip-link styles. The adoption baseline is recorded in `docs/baselines/design-lab-adoption.md` (Design Lab commit `ec590abd4c3c6fae97dd7c14d866443e3f67e1e0`).

This is a focused client slice. The canonical list of 11 Bounded Contexts and the catalog of 133 `CONFIRMED / V1` stories do not imply that every context or story has a finished Web feature or detailed acceptance criteria.

## Known gaps and integration limits

- Owner-authorized Buyer Direct Order scope is not part of v0.2.0 and is deferred to a later release; its Portal presentation/adapter and server permission-contract verification are future work, not gates for this source release.
- The current local Tenant has no delivery rows. The read-only Buyer tracking list returns `200` with an empty `items` list; the UI empty-state check passes. Detail/events coverage is explicitly skipped until a real Buyer Delivery is present.
- The order-flow browser scenario reaches the saved-address read, which returns `400 INVALID_REQUEST`. API investigation found a local fixture/API mismatch: the Buyer address seeder stores null department/province/district codes, the persistence adapter converts them to empty strings, and address rehydration rejects blank codes. Tenant scope and Buyer/account/address/catalog/stock rows were confirmed present. No fixture reseed or delivery fact creation was performed.
- API PR #117 remains open against `develop`. The current Web integration candidate pins signed API implementation commit `7eaca22609b39ca817beb9c6717e4bf9fef0529f`; the PR’s current GitHub head is `13227b00587b31924ccb4639712e96580dbefa4d` and GitHub reports `BEHIND`. The pin is for candidate integration checks and does not imply merge, release, or deployment.
- Platform catalog/policy administration, customer/address management, inventory adjustments/transfers, Notifications, and Business Traceability have no current Web workflow. Generic payment reconciliation and POD evidence capture are outside this client slice. Buyer has no document issuance UI; a generation request returning `202` is pending, not a ready PDF.
- Production gateway/API routing, CORS/cookie policy, production Tenant provisioning/cutover, Product/UX acceptance, and System Acceptance have not been verified for this candidate.
