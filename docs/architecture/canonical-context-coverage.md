# Canonical context coverage

This map relates the Web Platform and Buyer Portal to the accepted Nexa domain without creating a second Web domain model. The canonical catalog contains exactly 11 Bounded Contexts; the Blueprint owns their names, business rules and strategic contracts. Web routes, components and client folders are presentation and construction boundaries, not business authorities.

## Current Platform access-context implementation

The table above remains a snapshot of baseline commit `870d1a6`. The current Platform implementation has a typed browser adapter for `GET /me/access-contexts` and `POST /me/access-context-selections` in `libs/nexa-api/src/lib/contexts/tenant-access-governance/`, plus `PlatformSessionStore.listAccessContexts()` and `selectAccessContext()` in `apps/platform/src/app/contexts/tenant-access-governance/application/`.

The adapter sends the configured `X-Nexa-Surface` and current bearer authority; selection also includes browser credentials for the refresh-cookie rotation. The store lists contexts only for a complete authenticated Platform session, validates the returned membership/context fields, and fences the response against a changed session lease. Refresh, sign-in, sign-out and selection share one mutation lock so their cookie responses cannot race. Selection accepts a membership ID, executes once per returned observable, submits it to the API and loads `/session` before publishing the replacement scope and permissions. Only recognized pre-mutation rejection codes preserve the prior session; an unauthenticated, invalid-context, unrecognized or uncertain outcome clears the client token and does not treat that previous session as current. The scope fence compares user, Tenant, Workspace, membership and surface with a session epoch.

The existing Platform active-context page now loads eligible contexts after authentication and presents API-returned Tenant/Workspace names in a labeled native select. The `Use this context` action submits the selected membership ID through the store, remains available for the current membership when it is the only option, and disables while selection is pending. The page presents loading, retry and error states without using role strings for authorization. Its focused component tests cover the authentication boundary, single-context state and pending selection. Portal has no corresponding implementation. No local API runtime or browser end-to-end verification was run for this flow; implementation evidence does not establish Product acceptance or complete `WEB-US-018`.

## Construction rules

- Organize UI by user capability and surface. Do not create one route, package or app module per BC, and do not infer ownership from an endpoint or API package.
- Keep Platform and Portal separate. Platform serves workforce operations; Portal serves a Buyer authorized for the current supplier Tenant.
- Treat API responses as remote DTOs, projections or temporary form state. Carry the server-issued Tenant/Workspace context in requests and use it to fence stale responses. The client must not invent, override or persist an unvalidated Tenant/Workspace scope as durable authority; the API owns authorization and durable business decisions.
- Call owner APIs through typed client adapters. Preserve server revisions, idempotency keys, conflict outcomes and Problem Details where the contract requires them; an uncertain command result is not success.
- A composite query can display facts from multiple contexts while each source context retains authority. In particular, operations-dashboard reservation readiness is BC-05 data displayed beside BC-06 dispatch/delivery metrics.
- Keep cross-context processes behind the API. PR/SO commitment and applicable inventory and credit protection must not be implemented as coordinated client-side writes.
- Do not treat the 11 canonical contexts as 11 implemented Web features. For an unimplemented Web consumer, build only from the relevant frozen story and current API contract, and preserve unresolved acceptance criteria as open.

## Browser and Native access context contract

The browser and Native access paths share API operations but use different transport authority:

- Web sign-in remains `POST /api/v1/authentication/sign-in` with `identifier`, `password`, `workspaceSlug` and `surface`. Browser context listing uses `GET /api/v1/me/access-contexts` with the current Bearer token and `X-Nexa-Surface: PLATFORM` or `PORTAL`.
- A context list item contains `membershipId`, `tenantId`, `tenantName`, `tenantSlug`, `workspaceId`, `workspaceName` and `workspaceSlug`, ordered by tenant name, workspace name and membership ID ascending. Supply exactly one authority: Bearer or `X-Nexa-Context-Ticket`; both return `400 INVALID_REQUEST`, and neither returns `401`.
- Browser selection uses `POST /api/v1/me/access-context-selections`, body `{membershipId}`, current Bearer token and `X-Nexa-Surface`. The API requires an allowed browser Origin, revalidates identity, membership, Tenant/Workspace status, surface, roles, permissions and authorization version, and returns a new scoped session while rotating the surface refresh cookie. The Web request must include credentials so the browser accepts that cookie. An unavailable context returns `409 ACCESS_CONTEXT_SELECTION_REJECTED`.
- `POST /api/v1/authentication/identity-sign-in` and context-ticket authority are Native-only (`X-Nexa-Client: NATIVE`). Tickets are single-use, five-minute, header-only values. Invalid, expired or consumed tickets return `401 CONTEXT_TICKET_INVALID`; ambiguous ticket selection is not replayed. This is the accepted Mobile transport distinction, not a reason to send Native markers from the browser.

These contracts are documented in `blueprint/03-mobile/architecture/technical/api-client-contract.md` and implemented in API `origin/main`. The API-backed access operation does not change BC-01 ownership or authorize the client to select arbitrary tenant scope.
